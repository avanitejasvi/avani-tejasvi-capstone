# Issues & Reflections — building the multi-tenant branch

This is a retrospective, not a changelog (that's what `BUILD_LOG.md` is for). The goal here is to actually sit with what went wrong while turning `meal-match-agent` from a single-user CLI script into a hosted, multi-student app on `assessment-3-avani-tejasvi`, and be honest about why each thing went wrong and what it taught us — not just that it got fixed.

Grouped roughly in the order they actually surfaced: design-time issues we caught before they became real bugs, implementation issues we caught while building, and deployment issues we caught while actually trying to ship it. That order matters — the ones we caught earliest were the cheapest to fix, and the deployment ones were the ones that could have actually hurt someone if we'd rushed past them.

## Design-time: things that would have quietly broken the product, not the code

**The RSVP feedback loop stopped making sense the moment this became multi-tenant, and we almost didn't notice.**
The single-user build had one hardcoded `STUDENT_EMAIL` invited to every event, and its real YES/NO/MAYBE RSVP was the whole feedback signal. The instant every student gets their *own* calendar, that stops meaning anything — the calendar's owner accepting their own invite tells you nothing, because they're always going to be "accepted" by default. We caught this while writing the amendments, not while debugging, which is the version of this mistake we want to keep making: catching a design assumption that quietly stopped being true, before it's running in production and silently doing nothing useful. The fix (an automated "did they cancel it" check, plus later a manual rating page) is less elegant than the original RSVP idea, but it's honest about what signal is actually available.

**Google's "Testing" OAuth mode would have expired everyone's access after 7 days, invisibly.**
We picked "Testing" mode early on specifically to avoid Google's app-verification process. Reasonable instinct, wrong tradeoff — Testing-mode refresh tokens expire after a week regardless of use, which would have meant the whole app quietly stopped working for every student a week after they signed up, with no error message pointing at why. This is the kind of failure that's brutal specifically *because* it's silent — everything looks fine until it very much isn't. Moving to "In production" (unverified, but not time-limited) fixed it, at the cost of a scarier-looking consent screen users have to click through once.

**A shared file's boolean flag was doing two different jobs, and only one of them still made sense.**
`menu_intake_<date>.json`'s `processed` flag meant "has this date's board been read yet" when there was one user. Add more users and it's still being flipped once per user per run, which either means it lies (says "done" after the first user, even though nobody else has run yet) or gets flipped redundantly forever. Neither is a real bug in the single-user world — it only becomes wrong once you add the second user, which is exactly why nobody would have caught it just by testing carefully. We split it into two genuinely different things: a shared "has this date been extracted" fact (just: does a row exist), and a private, per-user "did I already run for this" fact (a real per-user claim row with a database-level uniqueness guarantee, not a flag anyone has to remember to set correctly).

**Deterministic event IDs, so a crash mid-request can't silently double-book someone.**
This one's a "what if" we thought through rather than something we watched happen: if the app creates a real Calendar event and then crashes before saving that fact to the database, a naive retry creates a second real event. We generated the event's ID from a hash of `(user, date, meal slot)` instead of letting Google assign a random one — so a retry produces the *same* ID, Google says "that already exists" (409), and we treat that as success instead of a failure. Boring to write, but it's the difference between "the retry logic is correct" and "the retry logic is correct until the one time it isn't."

## Build-time: things we found while actually writing the code

**Python 3.9 rejected syntax we wrote for a newer Python without checking.**
We wrote `X | None` in a couple of new files (`agent/db.py`, `agent/migrate_json_to_db.py`) — perfectly normal modern Python, and wrong for whatever Python version the test venv (and possibly Railway's runtime) actually is. It failed loudly and immediately the first time we tried to import anything, which is the best kind of bug: cheap, obvious, and caught before it ever reached a real deployment. Fixed by going back to `Optional[X]`, matching the style the rest of the codebase already used — a reminder that "matches the existing code" isn't just a style preference, it's also a compatibility check you get for free.

**We nearly shipped a preference model that could only ever get more pessimistic, never happier.**
This is the one we're least proud of almost missing. Removing the single-attendee RSVP (correctly, for the reason above) also removed the *only* thing that had ever told the system a student liked a dish — the automated replacement (checking if an event got cancelled) can only ever produce a decline. Nothing was left that could raise a rating from real experience. It took deliberately going back and auditing the rebuild against the original plan's "what makes this agentic" criteria — specifically "it updates itself" — to notice that criterion was now only half true. If we'd shipped it as-is, the app would have worked, looked fine in a demo, and slowly taught itself to recommend less and less over time for no real reason. The fix, a page where a student can directly say "I ate this and liked it," is small, but the process of finding the gap — going back and checking the actual design intent, not just "does it run" — is the part worth remembering.

**Documentation drifted from reality without anyone lying about it.**
`agent.json` still said the model was `gemini-3.6-flash` (deprecated and replaced weeks earlier, per `BUILD_LOG.md`, for reasons unrelated to any of today's work) and described the extraction output as missing a field (`day`) that the code had actually been returning for a while. Nobody edited that file dishonestly — it just stopped getting touched while the code kept moving. Worth remembering because it's the most boring kind of bug and also the easiest one to never notice: nothing breaks, it just quietly stops being true.

## Deployment: things that only showed up once we tried to actually ship it

**We assumed "it's committed" meant "it's on GitHub." It didn't.**
Every step of today's rebuild was fully committed and working locally — but the branch it all lived on, `assessment-3-avani-tejasvi`, had never once been pushed. Railway, meanwhile, was quietly building whatever *was* on GitHub: the `main` branch, six commits behind, from before any of this existed. Railway wasn't broken and neither was the code — we were just looking at two different snapshots of the project and hadn't noticed. The lesson isn't "remember to push," it's that "deployed" and "committed" and "written" are three different states, and it's easy to be confident about the first because you're sure about the third.

**A repo rename looked, for a few minutes, like two different repos.**
Railway said it was deploying `avani-tejasvi-capstone`; our local remote pointed at `AvaniTejasvi_Capstone_DESG319`. Different names, so the obvious read was "wrong repo connected." It turned out to be the same repo — GitHub had renamed it at some point, and it redirects pushes automatically, it just also prints a notice about it that's easy to skim past. Worth double-checking a surprising-looking mismatch with an actual API call before restructuring anything around it — the fix here would have been unnecessary and disruptive if we'd acted on the first, wrong read.

**A real secret was sitting in git history, and it had never actually gone public — but it would have, in the next thirty seconds, if we'd taken the easy way out.**
Pushing for the first time got blocked by GitHub's secret scanner: a real Google OAuth client ID/secret, a GCP API key, and a refresh token, committed in plaintext in `.env`, months ago, across two separate commits (our first pass at finding them only caught one — git's default log view quietly hides some commits unless you ask it not to, which is its own small lesson). GitHub offered a one-click "allow this secret anyway" link for each. That link would have worked, and it would have been the wrong call — this repo is public, and clicking it means choosing to publish live credentials rather than letting a safety check that was doing its job stop us. We used `git filter-repo` to strip the secret out of history properly instead, which is more work and also the only version of "fixed" that's actually fixed. The close call here was less about the secret and more about how tempting the shortcut looked right when we were mid-flow trying to get a push to succeed.

**The tool that fixes history also doesn't ask before deleting your working files.**
`git filter-repo` did exactly what it was supposed to — and its final step is checking out the rewritten history, which meant `.env` (no longer present in any commit) vanished off disk entirely, not just out of git. We'd backed it up to a scratchpad file immediately before running the rewrite specifically because this kind of tool tends to be thorough in ways that aren't always obvious from the command you typed, and it turned out to matter. The backup wasn't a formality.

## The pattern across all of it

Almost none of today's real problems were "the code is wrong." They were assumptions that used to be true and quietly stopped being true — a solo-user RSVP that stopped meaning anything with two users, a `.env` file that stayed out of trouble right up until the repo went public, a branch that felt "done" because it was committed, not because anyone had checked what GitHub actually had. The thing that caught most of these wasn't cleverness — it was going back and re-checking assumptions against reality (the plan's own stated goals, the actual git history, the actual deploy logs) instead of trusting that things were fine because they'd been fine before.
